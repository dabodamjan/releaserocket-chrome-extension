# Browser ports: Chrome, Edge, Firefox

One codebase, three stores. The repository's `manifest.json` stays the Chrome manifest; `npm run zips` produces a store-ready package per browser in `dist/`. This document covers what differs per browser, how to build each package, and what each store's submission asks for.

Facts below were checked against live documentation on 2026-08-14. Sources on `developer.mozilla.org` and `learn.microsoft.com` were fetched directly; `extensionworkshop.com`, `addons.mozilla.org`, and `docs.github.com` were unreachable from the environment this was written in, so facts resting on those are marked **[unverified]** — confirm at the linked page when submitting. Exception: the data-collection consent facts (request/check API forms, feature detection, Firefox 140 floor) were verified live against [Firefox built-in data consent](https://extensionworkshop.com/documentation/develop/firefox-builtin-data-consent/) on 2026-08-14 from an environment that could reach it.

## What differs per browser

### Background script

Chrome and Edge run `src/background.js` as an MV3 service worker. Firefox does not support MV3 background service workers ([MDN: background](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background), [Firefox bug 1573659](https://bugzil.la/1573659)); it runs the same file as a non-persistent background event page declared via `background.scripts`. The Firefox package declares both keys, the MDN-recommended cross-browser form: Chrome 121+ ignores `scripts` in MV3, Firefox 121+ ignores `service_worker`.

The background also needs `src/core.js` (for the consent helpers, below). In Chrome and Edge the service worker loads it with `importScripts('core.js')`; the Firefox event page has no `importScripts`, so the generated manifest lists it in `background.scripts` ahead of `background.js`.

This works for us because the background script holds no state between messages: the token is read from `storage.local` on every request and every message gets a complete response. Nothing is lost when Chrome tears down the worker or Firefox suspends the event page.

### API namespace

Firefox exposes extension APIs on `browser.*` (promise-based); Chrome and Edge use `chrome.*` (promise-based in MV3). All three entry scripts pick whichever exists:

```js
const ext = globalThis.browser || globalThis.chrome;
```

The async-response pattern in the background script (`sendResponse` + `return true`) is supported in Firefox as well as Chrome ([MDN: runtime.onMessage](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/runtime/onMessage)).

### Manifest

The Firefox package's manifest is generated by `scripts/build-zips.js` from the Chrome one, adding:

- `background.scripts` — `["src/core.js", "src/background.js"]` (see above).
- `browser_specific_settings.gecko.id` — `release-notes-drafter@releaserocket.io`. An explicit ID is mandatory for signing MV3 extensions on AMO ([MDN: browser_specific_settings](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/browser_specific_settings)). Chrome ignores this key entirely, per the same page.
- `browser_specific_settings.gecko.strict_min_version` — `"140.0"`. Firefox desktop 140 is the floor for the built-in data-collection consent experience ([Firefox built-in data consent](https://extensionworkshop.com/documentation/develop/firefox-builtin-data-consent/)): the `data_collection_permissions` declaration below and the `permissions.request({ data_collection })` call the popup makes before storing a token. An older Firefox that installs the add-on but cannot parse the consent declaration or API is worse than the higher floor, so 140 supersedes the earlier choice of 127 (the first release whose install prompt displays and grants an MV3 extension's host permissions — [Firefox 127 release notes](https://developer.mozilla.org/en-US/docs/Mozilla/Firefox/Releases/127), bug 1889402; still relevant as history, no longer the binding constraint).
- `browser_specific_settings.gecko.data_collection_permissions` — `{ "required": ["none"], "optional": ["authenticationInfo"] }`. Mandatory for new extensions submitted to AMO since 2025-11-03 ([MDN: browser_specific_settings](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/browser_specific_settings)). Per that page, `required` declares "the data that the extension requires to be collected and transmitted for its operation" (`none`, or a list of categories) and `optional` declares "the data that the user can opt to provide". The extension operates fully without a token, so `required` is `none`; but a user who enters a GitHub token has authentication information transmitted off the browser with every api.github.com request, which is exactly the opt-in case — hence `authenticationInfo` under `optional`. Declaring it `none`-only would be false and risks AMO rejection for a manifest inconsistent with observable behavior. The declaration alone is not sufficient: see "Data-collection consent at runtime" below for the request/check flow the code implements.

Edge uses the Chrome manifest unchanged. Microsoft's port guide requires only: no `update_url` field (we have none) and no "Chrome" in the extension's name or description (we have none) ([Port a Chrome extension to Edge](https://learn.microsoft.com/en-us/microsoft-edge/extensions/developer-guide/port-chrome-extension)).

### Data-collection consent at runtime (Firefox)

Declaring `authenticationInfo` as optional is only half of Firefox's consent model ([Firefox built-in data consent](https://extensionworkshop.com/documentation/develop/firefox-builtin-data-consent/), verified 2026-08-14): the extension must also *request* that permission in a user-activated handler before collecting or transmitting the data, and respect its absence afterwards. How this codebase implements it:

- **Feature detection:** the `data_collection` key in `permissions.getAll()`'s result exists only where the consent experience does. Chrome and Edge lack it and keep working with zero prompts. The pure helpers `supportsTokenConsent()` / `hasTokenConsent()` in `src/core.js` encode this (covered by `test/consent.test.js`).
- **Saving a token (popup):** the Save click calls `browser.permissions.request({ data_collection: ["authenticationInfo"] })` and stores the token only when granted; a decline leaves storage untouched and says so in the popup status. The request runs as the handler's first await because it must happen inside the user-activated click.
- **Using the token (background):** before attaching the saved token to an api.github.com request, the background re-checks the grant via `getAll()`. The user can revoke data permissions any time in the Firefox extension settings; a revoked grant sends the request tokenless (public-repo behavior at the anonymous rate limit) rather than transmitting authentication data without consent.

### Host permissions and prompting on github.com

Chrome and Edge grant `host_permissions` and content-script origins at install. Firefox MV3 treats host permissions as **optional**: from Firefox 127 the origins in both `host_permissions` and `content_scripts` are shown in the install prompt and granted there, but the user can revoke them any time per-site via the toolbar Extensions button, and an extension **update** that requests new host permissions gets them silently not-granted ([MDN: host_permissions](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/host_permissions)).

Consequences for this extension in Firefox:

- `github.com` revoked → the content script does not inject; the button simply never appears.
- `api.github.com` revoked → background `fetch` loses its CORS exemption (the exemption applies only to granted hosts, background requests only, per the MDN page above). Drafting still works, because the GitHub API answers cross-origin requests from any origin (`Access-Control-Allow-Origin: *`) — **[unverified]** live, documented at [Using CORS with the GitHub REST API](https://docs.github.com/en/rest/using-the-rest-api/using-cors-and-jsonp-to-make-cross-origin-requests).

### Referral tag

The releaserocket.io links are tagged per store so backlink traffic is attributable: `?ref=chrome-extension`, `?ref=edge-extension`, `?ref=firefox-extension`. The source carries the Chrome tag; the build rewrites it for the other two packages.

## Building the store zips

```
npm run zips
```

Outputs in `dist/` (git-ignored, deterministic — identical sources rebuild byte-identical zips):

| File | Store |
| --- | --- |
| `release-notes-drafter-<version>-chrome.zip` | Chrome Web Store |
| `release-notes-drafter-<version>-edge.zip` | Edge Add-ons (Partner Center) |
| `release-notes-drafter-<version>-firefox.zip` | Firefox Add-ons (AMO) |
| `dist/firefox/` | unpacked Firefox build for local testing |

Each zip contains the manifest at its root plus `src/` and `icons/` — no tests, docs, or tooling.

Local testing: Chrome and Edge load the repository folder directly (`chrome://extensions` / `edge://extensions` → Developer mode → Load unpacked). Firefox: `about:debugging#/runtime/this-firefox` → "Load Temporary Add-on…" → pick `dist/firefox/manifest.json` (the repo root won't work in Firefox — its manifest has no `background.scripts`).

## Store submission requirements

Do not submit anywhere without the privacy policy page on releaserocket.io existing first — Chrome requires it, Edge asks for it, and AMO has a field for it (see STORE_LISTING.md).

### Chrome Web Store (existing)

Covered by [STORE_LISTING.md](STORE_LISTING.md). Developer account: one-time $5 fee **[unverified]** ([registration docs](https://developer.chrome.com/docs/webstore/register)).

### Firefox Add-ons (AMO)

- **Account:** register at [addons.mozilla.org/developers](https://addons.mozilla.org/developers/) with a Mozilla account; free **[unverified]**.
- **Package:** upload `release-notes-drafter-<version>-firefox.zip`. The manifest must carry the gecko ID and `data_collection_permissions` (both included by the build — verified requirements, see above). Choose "listed" distribution so AMO hosts, signs, and lists it — the listing page is the backlink.
- **Review:** automated validation at upload, then human review post-signing **[unverified]** ([submission guide](https://extensionworkshop.com/documentation/publish/submitting-an-add-on/)). Source-code upload is required only when the package contains minified/generated code **[unverified]** ([source code submission](https://extensionworkshop.com/documentation/publish/source-code-submission/)) — this extension is plain unminified JS with no build step, so none should be needed; the icons are generated PNGs, and `tools/gen-icons.js` is public in this repo if a reviewer asks.
- **Listing fields** ([listing guide](https://extensionworkshop.com/documentation/develop/create-an-appealing-listing/), unreachable — limits **[unverified]**): name, summary (250 characters), description, categories, homepage, support email/site, privacy-policy text field, license (MIT, from this repo), screenshots, tags. Copy that fits is in [STORE_LISTING.md](STORE_LISTING.md#firefox-add-ons-amo-deltas).
- **Policies to honor:** no remote code (we load none), data disclosures consistent with the manifest declaration ([add-on policies](https://extensionworkshop.com/documentation/publish/add-on-policies/), **[unverified]**).
- **Updates:** each new version is a new zip upload; automated review re-runs **[unverified]**.

### Microsoft Edge Add-ons

All verified against [Register as a Microsoft Edge extension developer](https://learn.microsoft.com/en-us/microsoft-edge/extensions/publish/create-dev-account) and [Publish a Microsoft Edge extension](https://learn.microsoft.com/en-us/microsoft-edge/extensions/publish/publish-extension) (fetched 2026-08-14).

- **Account:** Partner Center, Microsoft Edge program. "There is no registration fee for submitting extensions to the Microsoft Edge program." Needs a Microsoft account (a GitHub account can be used to create one); individual account type verifies faster than company. Publisher display name ≤ 50 characters.
- **Package:** upload `release-notes-drafter-<version>-edge.zip`. Name and description shown in the listing come from the manifest and are read-only in Partner Center; the manifest `description` doubles as the store's short description.
- **Submission form:**
  - *Availability:* visibility Public, markets default all.
  - *Properties:* category (Developer tools), website, support contact — all except category optional.
  - *Privacy:* single-purpose description; a written justification per permission (reuse the Chrome justifications in STORE_LISTING.md); remote code: No; data-usage checkboxes; privacy policy URL — "required if the extension collects any privacy information", so give it the same releaserocket.io policy URL as Chrome.
  - *Store listing per language:* description 250–10,000 characters (the Chrome full description qualifies); logo 1:1, 300×300 px recommended (128×128 minimum); screenshots optional, max 6, exactly 640×480 or 1280×800 px (take them at 1280×800 and the same files serve Chrome too); optional promo tiles 440×280 / 1400×560 px; optional YouTube URL; search terms optional, ≤ 7 terms, ≤ 30 characters each, ≤ 21 words total.
  - *Notes for certification:* free text; mention the optional-token flow so testers understand it works without login.
- **Review:** "The certification process can take up to seven business days." Updates are new package uploads and re-certify on the same terms.
